========================================
PHẦN 1: BẢN CHẤT VÀ KHỞI TẠO GIT REPOSITORY
========================================
Mục đích: Biến một thư mục bình thường thành một kho lưu trữ được Git theo dõi, hoặc lấy một dự án có sẵn từ trên mạng về máy.

1. Có project sẵn trên máy (Local)
----------------------------------------
* Lệnh: git init
* Tác dụng: Tạo ra một thư mục ẩn tên là `.git` (đây là trái tim của Repository).
* Phạm vi hoạt động: Git init ở đâu (thư mục TOP LEVEL), Git sẽ quản lý tất cả file và folder con bên dưới đó. Thư mục cha (nằm ngoài) KHÔNG được theo dõi.

2. Có repository sẵn trên GitHub (Remote)
----------------------------------------
* Lệnh: git clone <repo-url>
* Tác dụng: Download toàn bộ source code và lịch sử từ mạng về máy. Tự động cấu hình kết nối sẵn với mạng (remote origin).

❓ CÂU HỎI PHỎNG VẤN #1: 
Hỏi: "Em hãy phân biệt khi nào thì dùng 'git init', khi nào thì dùng 'git clone'?"
Đáp: 
- Dùng `git init` khi em đang code dở một dự án hoàn toàn mới trên máy tính cá nhân và bây giờ mới bắt đầu muốn Git theo dõi nó.
- Dùng `git clone` khi dự án đó đã tồn tại trên mạng (do em tạo trước hoặc của công ty/đồng nghiệp) và em muốn tải toàn bộ nó về máy để bắt đầu làm việc.


========================================
PHẦN 2: BẢO MẬT VÀ KẾT NỐI VỚI SSH KEY
========================================
Mục đích: Xác thực danh tính của bạn với GitHub một cách tự động và bảo mật tuyệt đối, không cần nhập tài khoản/mật khẩu nhiều lần.

1. Ưu điểm của việc dùng SSH Key (Thay vì HTTPS):
----------------------------------------
- Không phải nhập mật khẩu hay token mỗi lần push/pull code.
- Mức độ bảo mật cao, là tiêu chuẩn bắt buộc khi đi làm tại công ty hoặc kết nối với hệ thống tự động (CI/CD, Server).

2. Các bước cấu hình (Ghi nhớ nhanh):
----------------------------------------
- Bước 1 (Tạo Key): ssh-keygen -t ed25519 -C "email_cua_ban@gmail.com" (Nhấn Enter liên tục để bỏ qua mật khẩu phụ).
- Bước 2 (Lấy Key): Lấy nội dung tại file ~/.ssh/id_ed25519.pub
- Bước 3 (Gắn Key): Lên GitHub -> Settings -> SSH and GPG Keys -> Paste mã vào.
- Bước 4 (Test): ssh -T git@github.com (Thấy báo "Hi username! You've successfully authenticated" là thành công).

❓ CÂU HỎI PHỎNG VẤN #2:
Hỏi: "Tại sao các công ty công nghệ thường bắt buộc nhân viên dùng cấu hình Git qua SSH thay vì đường link HTTPS thông thường?"
Đáp: 
- Thứ nhất là vì tính bảo mật: Giao thức HTTPS dựa vào mật khẩu hoặc token dễ bị lộ, trong khi SSH dùng cơ chế 'Khóa công khai - Khóa bí mật' an toàn tuyệt đối. 
- Thứ hai là vì tự động hóa: Khi code được deploy lên Server (thường là Linux không có giao diện), hệ thống dùng SSH Key có thể tự động tải code về mà không cần con người can thiệp nhập mật khẩu.


========================================
PHẦN 3: VÒNG LẶP CODE HÀNG NGÀY (ADD & COMMIT)
========================================
Mục đích: Lưu trữ các thay đổi code của bạn vào lịch sử một cách an toàn.

1. Lệnh: git add
----------------------------------------
* Mục đích: Gom các file bạn vừa thay đổi vào "Vùng chờ" (Staging Area) để chuẩn bị đóng gói.
* Các lệnh cơ bản:
  + git add filename.txt  -> Chỉ thêm 1 file cụ thể.
  + git add src/          -> Thêm toàn bộ các file trong folder 'src'.
  + git add .             -> Thêm TẤT CẢ các file thay đổi trong dự án (Có dấu cách trước dấu chấm).

2. Lệnh: git commit
----------------------------------------
* Mục đích: Chính thức đóng gói (niêm phong) các file trong vùng chờ, dán nhãn lịch sử và lưu vào kho lưu trữ (Local Repository).
* Lệnh cơ bản: git commit -m "Nội dung ghi chú ngắn gọn nhưng rõ ràng"

❓ CÂU HỎI PHỎNG VẤN #3:
Hỏi: "Theo em, tại sao Git lại sinh ra bước 'git add' làm vùng đệm (Staging Area) mà không cho phép commit thẳng (lưu thẳng) vào lịch sử luôn?"
Đáp: 
- Vùng đệm sinh ra để giúp ta kiểm soát chính xác những gì sắp được lưu. Ví dụ em sửa 5 file, nhưng 3 file là code chuẩn em muốn lưu (commit) trước, còn 2 file đang test dở dang em chưa muốn lưu. Nhờ có `git add`, em chỉ việc add 3 file chuẩn kia để commit, 2 file còn lại vẫn an toàn ở ngoài vùng làm việc.


========================================
PHẦN 4: QUẢN LÝ LỊCH SỬ VÀ TÌM KIẾM (GIT LOG)
========================================
Mục đích: Tra cứu, xem lại tiến độ dự án, hoặc tìm kiếm xem ai là người đã viết đoạn code đó vào thời gian nào.

Các lệnh cơ bản thường dùng:
----------------------------------------
- git log                     -> Xem lại toàn bộ lịch sử chi tiết (Nhấn phím 'Q' để thoát màn hình xem).
- git log --oneline           -> Hiển thị lịch sử siêu gọn gàng (Mỗi commit chỉ chiếm 1 dòng gồm Mã Hash và Lời nhắn).
- git log -3                  -> Chỉ xem 3 commit gần nhất.
- git log --author="Ten"      -> Lọc và chỉ xem các commit của một người cụ thể (Ví dụ: git log --author "Duc" --oneline).

❓ CÂU HỎI PHỎNG VẤN #4:
Hỏi: "Dự án của team có hàng ngàn commit, làm sao em tìm nhanh được 5 commit gần nhất do đồng nghiệp tên là 'Nam' thực hiện để kiểm tra lỗi?"
Đáp: 
- Rất đơn giản, em sẽ kết hợp các cờ lại với nhau bằng câu lệnh: `git log --author="Nam" -5 --oneline`. Lệnh này sẽ lọc đúng tác giả Nam, lấy 5 kết quả mới nhất và hiển thị dạng rút gọn 1 dòng cho dễ nhìn.


========================================
PHẦN 5: LÀM VIỆC NHÓM & LƯU TRỮ ĐÁM MÂY (GIT REMOTE)
========================================
Mục đích: Trả lời cho bài toán: Làm sao để chia sẻ code với đồng nghiệp? Cùng hợp tác (collaborate)? Và backup code an toàn lên Cloud (GitHub)?

Các lệnh quản lý kết nối (Remote):
----------------------------------------
- git remote -v               -> Kiểm tra xem máy Local đang kết nối với những kho Remote nào trên mạng.
- git push origin main        -> Đẩy (Push) toàn bộ lịch sử code từ nhánh 'main' ở máy mình, lên kho lưu trữ 'origin' trên mạng.

❓ CÂU HỎI PHỎNG VẤN #5:
Hỏi: "Khi em gõ lệnh 'git push origin main', chữ 'origin' ở đây có ý nghĩa thực chất là gì?"
Đáp: 
- Chữ 'origin' chỉ là Tên Biệt Danh (alias) mặc định mà Git tự đặt ra để đại diện cho cái đường link URL dài ngoằng của kho lưu trữ trên mạng (ví dụ: git@github.com:user/repo.git). Điều này giúp lập trình viên gõ lệnh nhanh hơn mà không phải copy lại cái link đó mỗi lần push code.


========================================
PHẦN 6: KINH NGHIỆM THỰC CHIẾN & FIX LỖI THƯỜNG GẶP
========================================
1. Lỗi: git: 'add.' is not a git command.
-> Sửa: Do viết liền "add.". Phải viết đúng cú pháp có khoảng trắng: `git add .`

2. Lỗi: Bị kẹt trong màn hình `git log`, gõ nhầm lệnh (VD `cls` thành `csl`) khiến sinh ra file lạ.
-> Sửa: Đang ở chế độ đọc log, luôn nhớ BẤM PHÍM 'Q' ĐỂ THOÁT ra ngoài dòng lệnh chính trước khi gõ bất kỳ lệnh nào khác. Xóa file rác vừa sinh ra đi.

3. Lỗi: Báo `modified` dù file đã đổi tên (từ .md sang .txt).
-> Sửa: Do Windows ẩn đuôi mở rộng. Bật "File name extensions" trong View của Folder, kiểm tra xem file có bị dính 2 đuôi (VD: readme.txt.md) không và đổi lại cho đúng.
